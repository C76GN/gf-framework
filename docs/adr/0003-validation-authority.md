# ADR-0003: Productize selective validation behind one module

- Status: Accepted
- Date: 2026-08-23

## Context

Validation Shadow, affected analysis, and GUT sharding currently exist as parallel observational implementations with separate commands, reports, schemas, and tests. They do not yet reduce the authoritative validation path, while local Full validation has become expensive.

## Decision

One Validation Module will own planning, lane execution, evidence joining, selection, reuse, partitioning, authority, and fail-closed fallback. Its external interface is limited to planning a request, running a planned lane, and joining evidence into a report.

A single Validation Catalog declares every action's dependencies, inputs, executor, produced artifacts, time budget, reuse policy, partition policy, and membership in local, Full, and Release intents.

Local validation prioritizes fast affected feedback. Remote Full remains the final merge authority; Release remains the strictest authority. GUT partitioning becomes authoritative only after repeated exact comparison with an unfiltered control, and infrastructure uncertainty falls back to unfiltered execution.

Threat handling is layered:

- External and persisted evidence, artifacts, release inputs, credentials, process output, and untrusted paths remain strictly validated.
- Owned typed values inside one invocation are trusted after admission.
- An owned subprocess may produce acceptable evidence only after its platform boundary is proven quiescent within the original absolute deadline. Failure to prove quiescence is cleanup debt, blocks result/evidence publication, and retains cleanup authority until a terminal observation. A POSIX process-group proof does not claim containment against a hostile descendant that deliberately leaves the group.
- The implementation does not claim protection from an active same-account attacker mutating local state during an invocation.

## Consequences

- A frozen Git child environment removes every inherited `GIT_*` variable before publishing the five owned policy values. Repository redirection, config injection, prompting, locking, and locale therefore cannot silently re-enter through ambient process state.
- Shadow, affected, and GUT-partition product value is retained, but their parallel top-level schemas and commands are transitional.
- Unknown input closure always executes; failed or ambiguous evidence is never reused.
- Changes to the Validation Catalog, implementation, or workflow disable trusted reuse and require a complete bootstrap run.
- Existing Full/Release action closure and required merge contexts stay unchanged throughout migration.

## Migration sequence

This decision is implemented incrementally. The first slice centralizes action identifiers, statically available command arguments, dependency declarations, existing check groups and suites, and ordered Full lanes without changing execution behavior. A missing static command means only that the runner materializes it later from live inputs; it does not select an executor. Executor selection, inputs, artifacts, partitioning, and reuse remain runner-owned until a real consumer is migrated with focused tests. This temporary representation is not the final Action specification.

The next consumer slice moved the default and per-action timeout floors into the Catalog. The runner still owns caller-requested timeout increases, suite-deadline clipping, and aggregate parallel-lane envelopes; those are distinct policies and are not folded into the action floor.

On Windows, bare command lookup prepends the execution cwd only when the frozen environment does not define `NoDefaultCurrentDirectoryInExePath`; presence, not value, controls suppression and environment names are case-insensitive. Mutating a caller-owned environment follows the same semantics: one folded alias is replaced by the canonical key, true duplicate aliases fail with a distinct environment-ambiguity error before mutation, and scrubbing inherited state removes every folded alias; POSIX remains case-sensitive. Private core-smoke, parallel-shard, GUT-worker, and storage-acceptance environments remove `GODOT_USER_HOME` before dispatch and bind or scrub all user/temp roots, observation variables, and Godot pins through that mutation boundary, preventing stale casing from creating duplicate selection authority or escaping the owned root. Explicit relative paths remain exact-file, cwd-bound pins and are not rewritten through `PATHEXT`; the suppression applies only to the platform's implicit current-directory search. Drive-relative forms such as `C:godot.exe` or a `C:bin` `PATH` entry depend on ambient per-drive cwd state and therefore cannot be interpreted from the frozen inputs: a selected candidate or any `PATH` entry participating in bare-command lookup with that form fails the entire resolution before filesystem I/O rather than being skipped in favor of another executable. This resolution boundary applies to every external executable directly dispatched by the maintenance runner, not only to Godot. A Catalog- or materializer-authorized `declared argv[0]` may remain bare, but before dispatch its `effective argv[0]` must be resolved to an absolute path using only the frozen environment and the supervisor's actual cwd. A miss creates no effective command identity and starts no child process: serial actions report structured `not_started`, parallel Full reports structured setup failure while establishing all shard contracts, and neither delegates unresolved input to `CreateProcess` for a second ambient lookup. Godot commands still pass through the dedicated `tools/gf_godot_process.py` adapter, which adds the `GF_GODOT_EXECUTABLE` override and Windows Steam foreground-engine selection without creating an ambient fallback; a missing explicit pin remains missing.

Every external executable selected and directly dispatched by one owner must use the same final owned environment object and actual cwd later passed to the supervisor. A cross-thread `ParallelShard` boundary must not share that mutable dictionary: it may take one private immutable value snapshot at admission and make one value-preserving materialization at spawn, without merging ambient state. Resolution, snapshot admission, and dispatch must bind the same environment entries, actual cwd, and absolute effective argv, but Python object identity is not required across thread or spawn boundaries. Relative and empty POSIX `PATH` entries bind to that cwd, and successful resolution places the absolute path in final `argv[0]`; an ambient-cwd `shutil.which` preflight or a second operating-system lookup is not an authority. Storage acceptance establishes and pins a real empty project cwd under one exact private binding before resolving a relative Godot pin, revalidates binding, identity, and emptiness before a missing-engine return, and permits population only into that already-pinned empty directory. The same binding remains active across import, owned-log ingestion, GUT, and final acceptance, with verification before and after each process boundary. This closes the identities of executables dispatched by the maintenance runner, including the outer `xvfb-run` wrapper, but does not claim that `xvfb-run`'s internal `Xvfb`, `xauth`, or other toolchain is hermetic.

Git is the deliberate stronger invocation-scoped exception to per-dispatch cwd lookup. The outer process environment is copied by value once; after the Catalog registries close and before any workspace Git I/O, `tools/gf_process_authority.py` resolves the mandatory `git` capability exactly once from the framework root. Its child environment is derived from that same snapshot with `GIT_OPTIONAL_LOCKS=0`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_TERMINAL_PROMPT=0`, `LC_ALL=C`, and `LANG=C`. Workspace fingerprinting, capture/materialization, affected analysis, project profiling, GUT workers, credential scanning, and release revision capture receive that immutable capability explicitly, use its absolute executable and exact environment, and never perform a later cwd/PATH search. Materialized workspaces therefore change Git's operation cwd without changing Git's executable authority. A standalone repository-oriented entry may establish the same capability at its explicitly supplied repository root, but nested calls and worker threads must reuse it rather than recapturing ambient state. Release artifact construction reads the source revision once and reuses that value for every manifest and audit comparison. The process supervisor's public one-shot APIs require an explicit environment mapping; omitting it is a pre-dispatch programming error, not permission to inherit `os.environ`.

A long-lived service is exposed only through the concrete `SupervisedProcessLease` facade; callers never branch on a private platform lease type. The caller-owned concrete publication slot accepts only that facade and is the authority commit point, so asynchronous control flow after publication cannot strand an unobservable child. All public process-start APIs, including one-shot execution and long-lived lease start, require an explicit environment mapping; omission is a zero-dispatch programming error, not permission to inherit `os.environ`. One immutable monotonic lifetime deadline governs start, cancellation, and cleanup. A separate earlier operation deadline reserves bounded cleanup time, and close reuses the original lifetime deadline. Concurrent and repeated close calls consume one published terminal result or error.

Windows long-lived leases keep a native Job Object boundary. Linux uses an independent watchdog helper that is the caller's direct child and the service's direct parent, starts in an isolated session with a minimal environment, owns the service process group, authenticates `CONFIG`, `READY`, `DEBT`, and `QUIET` with a nonce and shared deadline, and retains exact helper identity through pidfd. Non-Linux POSIX, a missing `/proc` directory, or missing `pidfd_open` fails before helper creation. The helper then proves that procfs is real, complete, and parseable before it forks the service; fake, hidden, or incomplete procfs may create a helper that is subsequently reaped, but never a service. After authority transfer the watchdog remains responsible if the caller is killed. Only terminal `QUIET` plus direct-service reap, empty owned-group proof, helper reap, and transport finalization establishes cleanup; status loss or protocol corruption revokes parent control, and cleanup debt blocks success evidence even when finalization still reaps the tree. This does not claim containment against a descendant that deliberately leaves the process group; that threat requires an invocation-owned cgroup or equivalent kernel boundary.

The authoritative GDScript LSP action always uses `--spawn-lsp --port 0` behind an invocation-owned process boundary and never attaches to or terminates an ambient editor. A direct serial action uses the current workspace and frozen invocation environment; materialized parallel Full paths add their private workspace and environment boundaries. Before protocol use, the tool derives the server owner PID from the actual established IPv4 loopback connection rather than a listener snapshot and requires it to equal the direct PID published by the lease. Windows and Linux owner lookup is deadline- and resource-bounded and continuously checks lease health. A report becomes `invocation_owned` only after local cancellation succeeds, the supervised boundary is quiescent, and the connected server PID, published PID, and final supervisor PID are identical. Attaching to an existing editor remains `non_authoritative`; `--connect-or-spawn` may truthfully report invocation ownership when it actually falls back to a fully owned spawn, but that ambient-capable convenience command is not the Catalog Full or Release lane.

The executor consumer slice makes every action explicitly declare either `in_process` or `subprocess`; there is no implicit default. The Catalog owns that choice, while the runner remains the composition root for trusted in-process callables, deferred command materializers, live invocation state, output capture, and supervised processes. The runner captures the Catalog and process environment once at invocation entry. Before any workspace or artifact I/O, it requires the in-process adapter registry and deferred-materializer registry to close exactly over that captured Catalog's projections, then freezes both registries with the same object as one invocation binding; a global Catalog rebind during registry construction cannot split the plan from the binding. Ordinary registry-construction failures use the same structured setup failure rather than escaping or falling back. Real command materialization is separate from non-executed fallback description: a deferred materializer is called exactly once only after an action is eligible for dispatch, while blocked, deadline-exhausted, Shadow, and invalid-shard paths use an executor-labeled placeholder that can never enter actual dispatch. Materialized command arguments are non-empty by default; the only empty-value exception is the canonical `release_metadata --artifact-manifest` value slot, which must equal the invocation context so that the established structured missing-artifact result is preserved. Serial command selection, timeout selection and dispatch, plus parallel shard supervisor budgets and report acceptance, consume the bound Catalog rather than rereading a global instance. Each dispatch-eligible action forms one immutable command identity before fingerprinting: `declared` preserves the Catalog- or materializer-authorized argv and may retain a bare executable name; `effective` is the exact argv selected under the frozen environment and execution cwd, and its `argv[0]` must be absolute before dispatch. Input fingerprint schema v2 binds both sides, while the existing result `command` field continues to report `effective`. Every subprocess executable uses only the supplied environment and actual cwd; it cannot fall back to a different ambient search path. Godot remains a specialization of that rule: its adapter also consumes the explicit override and chooses the foreground engine, while an override containing an explicit relative or absolute directory remains a pin whose missing target cannot fall back to a same-named executable on `PATH`. The parent invocation Catalog remains authoritative for executor kind and timeout floor. Before a shard starts, that same captured object projects only its root-bound static argv to the exact isolated workspace; this projection cannot carry or reconstruct executor, timeout, dependency, group, or suite policy. The runner appends sealed artifact arguments and freezes every assigned declared/effective identity against each shard's final private environment and real materialized cwd. It must materialize and freeze the complete batch plan behind one global admission barrier before the Godot isolation probe, any progress `started` event, or any call to the shard supervisor; a later-batch setup failure therefore proves zero dispatch globally. After admission, execution retains the stable resource batches and releases each batch immediately after report, source, log, and cleanup validation so an earlier cleanup failure cannot be discovered after a later batch starts. Report acceptance consumes the pre-dispatch contract and never reprojects the Catalog or reruns executable resolution after the child returns. Supervisor result name, command, and workspace must exactly echo each frozen parent-dispatched shard; returned metadata is not a new source of authority. The frozen parent-dispatched command tuple is the sole acceptance source for the requested action timeout, assigned suite timeout, and exact package artifact-manifest path. A shard's top-level suite timeout must equal that assignment; per-action remaining suite budget may only stay within the assignment and decrease monotonically. Accepted action results must also match their executor and frozen effective command, reject deferred placeholders, prove Catalog-consistent layered timeout, dependency provenance, and v2 input fingerprints from the frozen declared/effective pair, and embed complete stdout/stderr text with its exact length and digest. The parent rejects truncated stream fields and recomputes every stream digest and result fingerprint from the embedded text before the fingerprint can become a later action's dependency. This hidden internal mode requires a parent-shaped `--json-output`, serial job, and explicit check selection. The child encodes the final private JSON once and refuses it before any replacement write when its UTF-8 bytes exceed 16 MiB; the parent reader independently enforces the same ingress limit. Only after all results and their dependency chain are trusted does the parent restore public stdout/stderr fields to the ordinary 12,000-character diagnostic tails, retaining the verified full counts, digests, and fingerprints. Deferred actions remain excluded from parallel Full report acceptance until that path has an explicit frozen materialization contract. A deferred command remains independent from executor kind. Toolchain content identity, cross-host declaration keys, inputs, artifacts, partitioning, reuse, and callable ownership remain outside this slice, and the transitional action tuple is still not the final Action specification.

The affected-input consumer slice moves the existing advisory declarations for `package_user_dependency_boundary`, `public_api_boundary`, and `public_docs_boundary` into the Validation Catalog. The pure `PathRule` and `CheckInputSpec` schema belongs to the validation contract layer; the input analyzer owns capture and comparison behavior but no default declaration set. A Catalog rejects non-contract values, unknown actions, and duplicate action declarations, freezes declarations in action order, and exposes `None` only for a known action whose input closure is still undeclared. The runner must pass the declarations from the Catalog captured at invocation entry, so a later global rebind cannot change affected classification. This migration does not make affected selection authoritative: every requested check still executes, an undeclared action remains `unknown -> execute`, and skip, cache, and reuse counters remain zero. Complete input closure, toolchain identity, cross-host declaration keys, produced and consumed artifact policy, trusted evidence materialization, reuse, and authoritative selection remain later decisions.
