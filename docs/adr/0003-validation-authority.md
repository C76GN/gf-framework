# ADR-0003: Productize selective validation behind one module

- Status: Accepted
- Date: 2026-08-23

## Context

Validation Shadow, affected analysis, and GUT sharding currently exist as parallel observational implementations with separate commands, reports, schemas, and tests. They do not yet reduce the authoritative validation path, while local Full validation has become expensive.

## Decision

One Validation Module will own planning, lane execution, evidence joining, selection, reuse, partitioning, authority, and fail-closed fallback. Its external interface is limited to planning a request, running a planned lane, and joining evidence into a report.

A single Validation Catalog declares every action's dependencies, inputs, executor, produced artifacts, time budget, reuse policy, partition policy, and membership in local, Full, and Release intents.

Local validation prioritizes fast affected feedback. Remote Full remains the final merge authority; Release remains the strictest authority. GUT partitioning becomes authoritative only after repeated exact comparison with an unfiltered control, and infrastructure uncertainty falls back to unfiltered execution.

Threat handling is layered:

- External and persisted evidence, artifacts, release inputs, credentials, process output, and untrusted paths remain strictly validated.
- Owned typed values inside one invocation are trusted after admission.
- Process timeout, cancellation, and orphan cleanup remain mandatory.
- The implementation does not claim protection from an active same-account attacker mutating local state during an invocation.

## Consequences

- Shadow, affected, and GUT-partition product value is retained, but their parallel top-level schemas and commands are transitional.
- Unknown input closure always executes; failed or ambiguous evidence is never reused.
- Changes to the Validation Catalog, implementation, or workflow disable trusted reuse and require a complete bootstrap run.
- Existing Full/Release action closure and required merge contexts stay unchanged throughout migration.

## Migration sequence

This decision is implemented incrementally. The first slice centralizes action identifiers, statically available command arguments, dependency declarations, existing check groups and suites, and ordered Full lanes without changing execution behavior. A missing static command means only that the runner materializes it later from live inputs; it does not select an executor. Executor selection, inputs, artifacts, partitioning, and reuse remain runner-owned until a real consumer is migrated with focused tests. This temporary representation is not the final Action specification.

The next consumer slice moved the default and per-action timeout floors into the Catalog. The runner still owns caller-requested timeout increases, suite-deadline clipping, and aggregate parallel-lane envelopes; those are distinct policies and are not folded into the action floor.

The executor consumer slice makes every action explicitly declare either `in_process` or `subprocess`; there is no implicit default. The Catalog owns that choice, while the runner remains the composition root for trusted in-process callables, deferred command materializers, live invocation state, output capture, and supervised processes. The runner captures the Catalog and process environment once at invocation entry. Before any workspace or artifact I/O, it requires the in-process adapter registry and deferred-materializer registry to close exactly over that captured Catalog's projections, then freezes both registries with the same object as one invocation binding; a global Catalog rebind during registry construction cannot split the plan from the binding. Ordinary registry-construction failures use the same structured setup failure rather than escaping or falling back. Real command materialization is separate from non-executed fallback description: a deferred materializer is called exactly once only after an action is eligible for dispatch, while blocked, deadline-exhausted, Shadow, and invalid-shard paths use an executor-labeled placeholder that can never enter actual dispatch. Materialized command arguments are non-empty by default; the only empty-value exception is the canonical `release_metadata --artifact-manifest` value slot, which must equal the invocation context so that the established structured missing-artifact result is preserved. Serial command selection, timeout selection and dispatch, plus parallel shard supervisor budgets and report acceptance, consume the bound Catalog rather than rereading a global instance. Each dispatch-eligible action forms one immutable command identity before fingerprinting: `declared` preserves the Catalog- or materializer-authorized argv and `effective` is the exact argv selected under the frozen environment and execution cwd. Input fingerprint schema v2 binds both sides, while the existing result `command` field continues to report `effective`. Godot resolution uses only the supplied environment `PATH`, cwd, and explicit override; it cannot fall back to a different ambient search path. An override containing an explicit relative or absolute directory is a pin, so a missing target remains missing instead of falling back to a same-named executable on `PATH`. The parent invocation Catalog remains authoritative for executor kind and timeout floor. Before a shard starts, that same captured object projects only its root-bound static argv to the exact isolated workspace; this projection cannot carry or reconstruct executor, timeout, dependency, group, or suite policy. The runner then appends sealed artifact arguments and freezes every assigned declared/effective identity against the shard's private environment, while executor choice still comes only from the captured Catalog. Report acceptance consumes that pre-dispatch contract and never reprojects the Catalog or reruns executable resolution after the child returns. Supervisor result name, command, and workspace must exactly echo each frozen parent-dispatched shard; returned metadata is not a new source of authority. The frozen parent-dispatched command tuple is the sole acceptance source for the requested action timeout, assigned suite timeout, and exact package artifact-manifest path. A shard's top-level suite timeout must equal that assignment; per-action remaining suite budget may only stay within the assignment and decrease monotonically. Accepted action results must also match their executor and frozen effective command, reject deferred placeholders, prove Catalog-consistent layered timeout, dependency provenance, and v2 input fingerprints from the frozen declared/effective pair, and embed complete stdout/stderr text with its exact length and digest. The parent rejects truncated stream fields and recomputes every stream digest and result fingerprint from the embedded text before the fingerprint can become a later action's dependency. This hidden internal mode requires a parent-shaped `--json-output`, serial job, and explicit check selection. The child encodes the final private JSON once and refuses it before any replacement write when its UTF-8 bytes exceed 16 MiB; the parent reader independently enforces the same ingress limit. Only after all results and their dependency chain are trusted does the parent restore public stdout/stderr fields to the ordinary 12,000-character diagnostic tails, retaining the verified full counts, digests, and fingerprints. Deferred actions remain excluded from parallel Full report acceptance until that path has an explicit frozen materialization contract. A deferred command remains independent from executor kind. Toolchain content identity, cross-host declaration keys, inputs, artifacts, partitioning, reuse, and callable ownership remain outside this slice, and the transitional action tuple is still not the final Action specification.
