# Dialogue 恢复分层与项目配方

三层解决不同问题；跨版本存档不能修改 `resource_fingerprint` 后冒充同内容快照。

| 层 | 保存内容 | 恢复承诺 | 所属方 |
| --- | --- | --- | --- |
| 严格运行快照 | 框架快照与项目资源键 | 同内容身份、稳定 TEXT 或已停止状态，恢复不重放信号及 mutation | GF 提供机制，项目持久化 |
| 项目检查点 | 项目 schema、内容版本、稳定检查点 ID、业务状态、效果收据 | 按已声明安全位置开启新会话；允许放弃逐行执行位置 | 项目定义映射与副作用策略 |
| 版本迁移 | 明确的旧版本输入和新版本输出 | 仅执行已发布的版本、字段和检查点映射，未知输入拒绝 | 项目维护转换与验收 |

小型项目可先只使用严格快照，并在发布新内容时明确要求重新开始章节。需要长期内容演进的项目应尽早定义检查点和存档版本；不必为每条文本赋予永久迁移承诺。

## 可运行的项目策略示例

仓库中的 `tests/gf_core/extensions/dialogue/fixtures/project_checkpoint_recipe.gd` 是固定章节配方，配套 `test_gf_dialogue_project_recovery.gd` 通过公开 Runner API 验证。它不属于框架 API，也不由运行时自动发现。

示例项目明确规定：v1 的 `reward_claimed = true` 表示奖励已提交，`coins` 是余额；v2 将余额字段改为 `balance`，把已提交奖励记为 `effect_ids = ["chapter-1.reward"]`。旧检查点 `reward_claimed` 被作者显式映射为新检查点 `after_reward`，后者对应新资源行 `chapter_1_after_reward`。它不按名称相似程度寻找新行。

```json
{
  "schema_version": 1,
  "content_revision": "chapter-1@1",
  "checkpoint_id": "reward_claimed",
  "project_state": {"coins": 5, "reward_claimed": true}
}
```

项目恢复依次执行：

1. 从持久化层读出经过项目大小、类型与来源校验的存档；保留原件。
2. 对受支持版本执行纯数据转换，完整校验新状态；未知版本、检查点或字段类型返回失败。
3. 解析项目内容版本对应的资源，验证资源图，查找作者明确列出的安全 TEXT 行。示例拒绝条件行、自动行和带条件响应的目标。
4. 创建全新 Context 与 Runner，用 `start(resource, explicit_line_id, context)` 开始候选会话。准备期间不安装外部 handler 或信号订阅者；因此不会重放位于该行之前的奖励 mutation。
5. 候选到达指定行后，项目一次性切换自己的活动会话引用，再安装业务回调、刷新 UI，并按持久化策略写入新版本存档。任何准备失败都继续使用旧会话和旧存档。

示例的 `prepare_checkpoint()` 返回候选 Runner、Context 与转换后的存档，不接收也不修改旧会话。`migrate_save()` 不修改输入；同版本检查点也使用同一明确映射。新会话可生成自己的严格快照，旧快照的指纹始终不变。

这里的无副作用准备来自示例主动限制了资源目标和回调。若项目加入自定义 Context、条件、文本解析、Signal 订阅者或自动推进，必须重新证明这些操作的副作用边界；不能把任意 hook 包装成框架事务。资源也应在准备和发布期间保持不可变。

## 副作用与失败验收

示例 `claim_reward_once()` 在同一内存状态中一次替换余额和效果收据。已记录奖励不会再次增加余额；它只展示项目内存状态的幂等策略，不承诺文件写入、支付、服务端或其他外部系统原子提交。真实外部副作用需要持久化幂等键、事务或可核实的对账协议。

配套回归验证同资源快照恢复、内容变更拒绝且保留原会话、明确旧版本迁移、新版本检查点直接恢复、奖励不重放，以及未知映射、非法状态和非安全目标拒绝。项目还应覆盖自己发布过的每条版本迁移边、内容资源包缺失与持久化失败；框架不会补猜缺失的路径。

运行快照的字段、稳定窗口与上下文子类恢复要求见 [Dialogue 主文档](index.md)。
