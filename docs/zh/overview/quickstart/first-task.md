# 完成第一个任务

运行一个能加分、更新界面、保存设置并正常退出的计数器，然后把同一个任务演进为异步服务。先完成这条闭环，再按实际需要添加 Model、System 或 Installer。

## 运行与观察

从 [GF 源码仓库的 first_task 目录](https://github.com/C76GN/gf-framework/tree/main/examples/first_task)取得样例。在仓库 Godot 项目中打开 `examples/first_task/first_task.tscn`，按 F6。

1. 选择“基础会话”，点击“加 1”，确认数值与界面同时更新。
2. 点击“保存并退出”，重新运行，确认计数恢复。
3. 选择“异步服务会话”，再次加分；完成前可以取消最近工作。
4. 在工作未完成时退出：停止接纳新工作，等待已接纳工作完成，保存成功后关闭。

样例只使用 Kernel 与 Standard，不依赖可选扩展。它不修改项目主场景、全局 Installer 列表或默认空 Boot。发行包继续提供完整 `addons/gf`；此独立学习样例在源码仓库中维护。

## 文件与职责

| 文件 | 负责什么 | 何时需要拆分 |
| --- | --- | --- |
| `first_task.gd` | Godot 控件、按钮、窗口退出 | 多场景共享界面或多个独立交互流程 |
| `task_session.gd` | 计数状态、服务装配、保存与关闭 | 状态被多个业务模块共享时考虑 Model，规则有独立生命周期时考虑 System |
| `task_service.gd` | 异步工作接纳、取消、排空 | 换成项目自己的异步后端时保持相同关闭合同 |

基础会话注册设置 Store 与 `GFSettingsUtility`，直接持有自身业务状态；异步会话增加一个项目服务。小功能不必先搭齐所有角色。需要集中装配后再使用[最小启动与 Installer](minimal-installer.md)；`Gf` 管理项目全局架构，样例采用独立 `GFArchitecture` 便于完整创建和关闭学习会话。

## 失败也属于完整任务

设置写入 `user://gf_first_task.json`。首次文件缺失时显式使用默认值；损坏文件不自动覆盖。计数必须是 0 至 1,000,000,000 的整数，在途增量也占用额度。保存失败保留内存计数与错误说明，不报告保存成功，也不继续正常退出。架构关闭失败保留终态，重复退出仍返回失败；只有用户明确选择强制退出才越过失败，且不保证内存状态落盘。

异步服务最多接纳四份工作，满载时明确拒绝；取消不会增加计数，退出前已经接纳的有效工作仍完成一次。重复退出不会并发执行多次保存和关闭。样例的异步工作使用帧推进模拟延迟，不代表后台 IO 可以被强制终止。进程被强制结束不保证内存状态落盘。

## 接入成本应怎样比较

对比原生 Godot、这个较薄的 GF 接入和更完整的 GF 装配时，保持以下合同一致：

| 维度 | 所有方案必须覆盖的工作 | 单独比较的额外能力 |
| --- | --- | --- |
| 基础任务 | 状态到 UI、缺失文件、损坏文件、保存失败与重试 | 通用设置 Schema、存储端口替换 |
| 异步演进 | 有界接纳、取消、迟到完成、关闭期间拒绝、排空后保存 | 依赖 DAG、跨模块激活与诊断 |
| 项目演进 | 重启恢复、重复退出、场景释放与错误反馈 | 多架构、模块热事务、工具贡献 |

先记录新增文件、必须理解的概念、修改触及的职责、失败定位步骤和测试结果。代码行数只作为辅助数据。不能让省略错误场景的原生演示与完整框架方案直接竞争，也不能把框架额外能力当作每个小项目都需要的收益。

本样例证明上述闭环不要求创建全套 Model/System/Command；它尚不能证明原生方案在大型项目中更差，也不能证明所有 GF 模块都值得保留。实际项目若薄接入成本更低，就改善默认教程和入口；某个模块长期高成本低收益，则独立替换。只有多个任务的同条件证据都指向核心设计问题时，再评估重写。
